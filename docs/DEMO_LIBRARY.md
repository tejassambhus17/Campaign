## Reviewed rollout

No live database has been read or changed by this subtask. Root deployment must
first obtain the scoped live rollout approval, preserve an existing-cloud backup,
deploy the compatible backend/migration007 and verify old clients. Never ship a
ready release that depends on endpoints absent from the live backend.

From `services/api`, use the existing Python environment. No command loads a
`.env`, migrates schema, creates a reviewer, or silently selects a default DB:

```powershell
.\.venv\Scripts\python.exe demo_library.py --sqlite <existing-project-local-path> --dry-run
# Only after reviewing that exact plan:
.\.venv\Scripts\python.exe demo_library.py --sqlite <same-path> --apply `
  --confirm-manifest campaign-library-v1 --expected-plan-sha <reviewed-planSHA256>
```

For the explicitly authorized existing cloud only, replace `--sqlite <path>`
with `--configured-cloud`; the established private environment supplies the
existing connection without printing it. Dry-run uses a read-only transaction
and preserves schema search-path rules. It reports actual eligible counts,
inserts, preserved records, per-demo assessments, skipped edits, media checks,
conflicts/prerequisites and a plan SHA256. Only reviewed apply opens a write
transaction, takes the established lock and recalculates that digest. Concurrent
user activity changes the plan and safely aborts apply for a fresh review.

Apply inserts missing fourteen records and new registry/assessment rows only.
It does not update campaign data, public/working content, deadline, status,
contributions, original user rows or existing assessment timestamps. Missing old
seeds are not reconstructed with fake funding history. A stable-ID/owner mismatch
blocks atomically. Repeating an unchanged rollout inserts no campaigns and
reuses the same assessment publication IDs. No notifications are seeded on behalf
of the real user.

Rollback should disable the new UI or deploy backward-compatible code while
retaining additive schema and records. **Do not delete seeded campaigns after
they acquire activity**, remove payment/ledger rows, or reset databases. Any
later content change requires a new reviewed manifest/version rather than an
overwrite switch. Use the existing controlled cloud rollback procedure.
